# Scrum Guild をサービスにする方針

状態: 方針。値段と目安は仮で、ベータで確かめて直す。

## 決めたこと（2026-10-21）

- OSS をやめ、自分たちで運用するサービスにする。リポジトリは private のままにし、権利はすべて ucan-lab が持つ（`LICENSE`）。
- 稼働先は Cloudflare（Workers と D1）だけに絞る。Docker などで自分で立てる道は持たない。
- 1つのアプリと1つの D1 に複数の組織（顧客）を入れる。顧客ごとに Worker と D1 を立てる形は、顧客が増えるたびに立てる手間がかかるため選ばなかった。会員は30日のお試しでチーム用の組織を作れる。ベータの決済は Stripe などの決済サービスで行い、アプリは組織ごとの契約状態・上限・請求管理の権限を扱う。

## 経緯

はじめは自分のチームのためのタスク管理を OSS（MIT）で作り、立てる人が自分の Cloudflare か Docker に立てる前提だった。副収入にし、手応えがあれば事業にしたいと考えたため改めた。

- OSS のために背負っていた重さ（2つの稼働先、4つのアダプター、両方で通る SQL だけの縛り、公開前の点検）がなくなり、1人で作る量が減る。
- 失うのは、データを預けたくない会社に「自分で立てられる」と答える道と、OSS としての見つけてもらいやすさ。前者は、預かるデータを安全に扱うことで答える。
- 後で公開したくなったら、ソースは見られるが同じサービスを売ることを禁じるライセンス（FSL など）も選べる。MIT で一度出したものは取り消せないため、先に閉じておく。

## 誰が払うか

Backlog と GitHub を併用する、日本の受託開発や SES のチーム。「記録」（何をいつ終えたかを区分と月で残し、CSV で書き出す）が請求の根拠を作る手間を減らす。

## 値段の考え方

競合と比べた材料は [競合サービスの調査](competitors.md)。
2026-10-23 に決めた料金を土台に、2026-11-03 にプラン名、追加容量、組織ごとの契約と請求管理の方針を決めた。
価格はベータで検証する。
この節は提供時の方針で、課金と請求管理はまだ実装していない。

- 乗り換える先として売り、値段は Backlog と Redmine 系と比べて決める。発注元の Backlog を使うチームには、乗り換えずに Backlog と GitHub の上に重ねる使い方を残す。
- チーム用は1人ごとではなく、組織ごとの定額を人数の段階で分ける。ゲームの仕組みは全員が入って効くので、1人ごとの課金で一部の人だけ入れる使い方を招かない。

### 基本プラン

| 項目 | パーソナル | チーム | ビジネス |
| --- | --- | --- | --- |
| 想定する使い方 | 自分のタスク管理 | 小規模なチーム | 複数案件を持つチーム |
| 利用人数 | 本人1人 | 15人まで | 50人まで |
| 月払い | 無料 | 3,000円／組織 | 10,000円／組織 |
| 年払い | 無料 | 30,000円／組織 | 100,000円／組織 |
| 年払いの月あたり（計算） | 無料 | 2,500円 | 約8,333円 |
| 標準の添付容量 | 1GB | 30GB | 100GB |
| 有料での容量追加 | 可能 | 可能 | 可能 |
| 利用中のワークスペース | 3個まで | 数の上限なし | 数の上限なし |
| メンバーの招待 | 不可 | 可能 | 可能 |
| 無料で使える期間 | 期限なし | 30日のお試し | 30日のお試し |

- チームとビジネスで使える機能は同じ。差は人数と標準の添付容量だけ。51人以上は個別に相談。
- 人数の段階は Backlog のエコノミー（15人）に、チームとビジネスの標準容量は Backlog のエコノミーとビジネスにそろえる。乗り換えで人数の枠と容量が減らないようにするため。
- パーソナルは、会員が自分だけで使う「自分用」の組織。1アカウントにつき1つで、お試し中のチーム用の組織とは別に数える。招待も管理者の指名もできず、チームで使うならチーム用の組織を作る。アカウントを多く作れば無料の自分用も増えることは受け入れる。
- パーソナルのワークスペース数は、終了していないものだけを3個まで数える方針。終了すると枠が空き、再開には空き枠が必要。終了したもののデータは残す。現在の実装は終了したものも数えており、変更は [#771](https://github.com/scrum-guild-dev/app/issues/771) で行う。
- チーム用に無料プランは置かず、会員が作る組織には30日のお試しを用意する。1アカウントにつきお試し中の組織は1つまで。お試しの期限が来たら組織を一時停止し、支払いを受けたら再開する。運用者が作る組織は契約に応じて用意する。
- 年払いは2か月分を無料にする。途中で解約しても返金せず、期間の終わりまで使える。
- 消費税: ベータの間は適格請求書発行事業者に登録せず、表の値段を総額で請求する。事業にするときに登録し、表の値段を税抜として10%を加える。追加容量にも同じ扱いを適用する。

Wiki の最新本文と過去版も、題を含むUTF-8のバイト数を標準の添付容量と追加容量に算入する。論理削除後30日の保持中も算入し、保持期限後の掃除で使用量を減らす（2026-11-03、人の判断）。

### 追加容量

全プランで、標準の添付容量に次の容量を有料で追加できる。
個人で容量を使い切った場合も、パーソナルのまま購入できる。

| 追加容量 | 月払い | 年払い |
| --- | --- | --- |
| ＋10GB | 300円／組織 | 3,000円／組織 |
| ＋50GB | 1,000円／組織 | 10,000円／組織 |

- 複数口を組み合わせて購入でき、組織内の全ワークスペースで共有する。別の組織とは容量を共有しない。
- 買い切りではなく継続課金。年払いは基本料金と同じく2か月分を無料にする。
- 容量追加で人数やワークスペース数の上限は変わらない。終了したワークスペースに保存されている添付ファイルも、使用量に含める。
- 決済、購入した容量の反映、追加契約の解約は自動化する。チーム用は基本料金とまとめて請求し、パーソナルは追加容量の料金だけを請求する。

| 利用例 | 添付容量の合計 | 月払いの合計 |
| --- | --- | --- |
| パーソナル＋10GB | 11GB | 300円 |
| パーソナル＋50GB | 51GB | 1,000円 |
| チーム＋50GB | 80GB | 4,000円 |
| ビジネス＋50GB | 150GB | 11,000円 |

### 契約と支払いの管理

- 契約・支払いは個人アカウントで管理し、基本プランと追加容量は組織ごとに契約する。同じアカウントで複数組織を契約でき、各組織に料金が発生する。チーム2組織なら月6,000円、チームとビジネスが1組織ずつなら月13,000円。
- 請求担当者と実際に使う人を分けるため、組織ごとに「請求管理者」を置く。1人が複数組織を担当でき、1組織にも複数人を置ける。担当者が交代しても、契約と請求履歴を引き継げるようにする。
- 請求管理者は、担当組織の契約内容と必要な使用量、支払い方法、請求書・領収書、プラン・追加容量、更新・解約を管理する。請求専用の人には、タスク本文、添付ファイル、Wiki などの業務データを見せない。
- 請求専用の人は利用人数の枠に数えない。組織管理者やメンバーも兼任する人は、利用者として既存のルールで数える。組織管理者やメンバーであるだけでは、請求管理の権限を持たない。
- 利用人数は、組織管理者と、いずれかのワークスペースに所属しているか招待されている人を数える。無効にした人と、すべてのワークスペースから離れた管理者でない人は数えない。上限に達したら、まだ数えていない人を新しく招待できない。
- 請求管理者の権限と引き継ぎは未実装。ベータの課金導入時に [#772](https://github.com/scrum-guild-dev/app/issues/772) で扱う。現在の組織管理者や利用人数の実装を、この文書の変更だけで変えたことにはしない。
- 決済は Stripe などの決済サービスで自動化する。クレジットカードは月払いか年払い。請求書と銀行振込は年払いだけ受け、決済サービスの請求書の機能で送る。
- 原価は Workers Paid（月 $5）と使った分が中心。保存容量だけでなく D1 の読み取り、添付ファイルの読み書き、問い合わせ対応も含め、ベータで実測して採算を確かめる。カード決済と Stripe Billing の手数料は合わせて4.3%として見積もる。
- 他のツールからのデータ移行は、アプリに作らない（`requirements.md` の Non-Goals）。ベータの間は運用者が手で移し、無料で引き受ける。正式からは別料金で、値段の根拠はベータで移した範囲とかかった時間の記録。

## 進め方

1. 初版を作る。まず自分のチームで使う。課金はまだ作らない。
2. ベータ（副収入）。知り合いのチームなど 5〜10 の組織に提供する。値段は正式と同じで、決済・容量反映・解約は Stripe などの決済サービスと連携して自動化する。正式で値上げしても、ベータの組織は値上げから1年は今の値段のまま据え置く。目標は月に数万円。
3. 事業にするか決める。目安は、有料の組織が 30 以上、月の解約率が 3% 未満、紹介や問い合わせで自然に増えていること。

事業にするときに要るもの: 組織を立てる手順の自動化、セキュリティチェックシートへの回答、インボイス制度に合う請求、秘密保持の取り決め、必要なら法人化。

利用規約とプライバシーポリシーは、初版で用意する（会員登録で、知らない人が自分の組織を作れるようにするため。#646）。文面は `src/lib/legal/` の Markdown に置き、ログインしていなくても `/terms` と `/privacy` で読める。文面の案はセッションが書き、運営者の名前と問い合わせ先は仮の書き方のまま、人が決めて入れる。特定商取引法の表記は、課金を作るときに考える。

## 設計に入れておくこと

- 決済処理と支払い方法の保持は Stripe などの決済サービスに任せる。アプリには、組織ごとの契約状態と利用上限、請求管理者の権限を持たせ、購入・変更・解約の結果を自動で反映する。請求管理の実装は #772 で分けて進める。
- 取り込み元（Backlog、GitHub など）の認証情報は暗号化して持ち、解約したときの消し方を決める。
- 取り込み元の本文は既定で預からない。タイトルなどタスクとして扱うのに要る属性だけを持ち、本文も預けたい組織だけが組織の設定で選ぶ。顧客のデータを外部のサービスへ複製できない受託や SES のチームでも入れやすくし、セキュリティチェックシートで「本文を預からない」と答えられるようにする。
- GitHub のログインは、共通の1つの OAuth App にする（2026-10-22 に決めた。`development.md` の「GitHub のログインと取り込み」）。

## 未決

- 追加容量を契約途中で購入・変更する場合の精算、基本プランと追加容量の請求周期が違う場合の扱い。
- 容量の追加契約を減らし、使用量が上限を超える場合の猶予期間と新規アップロードの扱い。既存データを即時削除する設計にはしない。
- 顧客のデータ（private なリポジトリの課題や PR）を預かって運用する体制。
- 最初に声をかけるチーム。
- 適格請求書発行事業者に登録する時期。副業の確定申告と合わせて税理士に確かめる。
