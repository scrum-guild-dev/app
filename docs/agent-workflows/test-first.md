# 書き手を分ける変更

該当する変更だけ読む。Claude と Codex を相互に起動せず、現在の製品のサブエージェントで役割を分ける。各役に担当ファイルを渡し、他の作業を戻さないよう伝える。道具が無ければ不足を報告し、独立性を満たしたと扱わない。

やることが次のどれかに触れるなら、渡す前に下の「テストを先に書く」を行う。テストの書き手と実装の書き手を分け、実装の思い込みをテストに持ち込ませないため（すり抜けとランタイムの癖は、同じ書き手だとテストからも実装からも同じように抜け、レビューまで見つからない）。

- 守る仕組みのファイルを変える（`.claude/hooks/`、`.githooks/`）
- 認証、権限の検査、組織で絞る層のファイルを変える（`src/server/auth/`、`src/server/db/`、`src/server/operations/register.ts` と `guards.ts`）
- Workers のランタイムに頼る処理を書く（外への `fetch`、Cookie、リダイレクト、ストリーム、`scripts/headers.ts` のセキュリティのヘッダー）

`add-operation` で操作を足し、権限を選ぶだけの Issue は当てはまらない（型紙が権限と組織の分離のテストまで一続きで作る）。当てはまらないものは、テストも実装と一緒に書かせる（受け入れ条件の1つ目）。

Issue が無い直接依頼では、Issue の番号を「無し」と渡し、会話で整理した目的・完了条件・人の判断・置いた前提で代える。起票や Issue への書き込みを前提にしない。

## テストを先に書く

テストの書き手と崩す書き手は、同じ製品の汎用のサブエージェントにする。どちらにも、受け入れ条件のうちコミットしないこと、`pkill` を使わないことを渡す。下の 1 から 5 を (1) から (5) と呼び、外の手順の番号と分ける。

1. **書く。** テストの書き手に、テストだけを書かせる。渡すのは、ワークツリーの絶対パス、Issue の番号、完了条件、Issue の `人が決めたこと` と `セッションが置いた前提`、呼び口（操作の定義、関数の名前と引数、置くファイル）の5つ。実装の案は渡さない（理由: 渡すと、テストがその案の追認になる）。呼び口が Issue で決まっていなければ、先に決めて記録してから渡す（Issue への書き込みは承認範囲に従う）（理由: テストの書き手が推測で名前を置くと、実装の書き手がそれに合わせるか、テストを書き換えるかになる）。次を書かせる
   - 完了条件と、その2節の判断の1つずつに、通る場合と断る場合
   - フックと守る仕組みなら、すり抜けの手口を並べたもの。リダイレクト、ヒアストリングとヒアドキュメント、`cd` と `pushd`、`scp`、`rsync`、`tee`、引用符と否定、変数とエイリアス、ほかのシェルとインタープリタ。前に塞いだ手口を壊していないことも入れる（`.claude/hooks/guards.test.mjs` の既存の例）
   - Workers のランタイムに頼る処理なら、テストは Workers の実行環境で走らせる。`fetch` をモックにするときは、モックが返す振る舞い（`redirect` の各値、ヘッダー、本文を読める回数など）が本物の workerd と同じかを、モックを使わない小さなテストで先に確かめる
   - 新しい関数や操作を呼ぶなら、呼び口のとおりの空の入れ物（型だけ合わせ、`throw new Error('未実装')` を返すもの）を置かせる。import の失敗で全部が落ちると、振る舞いの無さで落ちたのかが分からないため。入れ物もテストと一緒に保存し、実装の書き手が中身を書く
   - 書いたテストを走らせ、新しい振る舞いを確かめるテストが、その振る舞いが無いためにアサーションか入れ物の `未実装` で落ちることを確かめる。通る場合と前に塞いだ手口のテストは、今のコードで通ってよい。書き間違いで落ちているものは直させる
2. **保存する。** 新しい振る舞いが無いために落ちた実行ログを確認し、テストと入れ物の状態を保存する。コミットを許されたセッションは `test:` のコミットの SHA を控える。未承認なら作業ツリー外の一時ディレクトリへテストをコピーし、対象一覧と保存先を控える。元の差分は保持する。この最初の保存先・SHA は固定し、後の周回で置き換えない。
3. **実装させる。** [acceptance.md](acceptance.md) の引き継ぎ情報を、同じ製品の実装専用エージェントに渡す。
4. **崩しにかかる。** 戻ったら、崩す書き手に、実装を崩すテストを足させる。渡すのは、ワークツリーの絶対パス、Issue の番号、完了条件、実装前に保存したテストと、実装の差分・新規ファイルの範囲。周ごとに新しいサブエージェントにする（理由: 前の周の見方を引きずらせない）。
   - 足したテストのうち、通ったものは、前のテストと重ならない手口を確かめるものだけを残させる（回帰を止める）
   - 落ちたテストには、落ちる理由が実装の欠陥である根拠（Issue、`docs/`、ランタイムの振る舞いのどれに反するか）を添えさせる。根拠を自分で確かめ、成り立たないものは捨てる（理由: 誤ったテストを渡すと、実装の書き手はテストを変えられないので、実装を歪めるか止まるかになる）
   - 残った落ちるテストを周回別の保存先・SHA に保存し（(2) の最初の基準は維持する）、実装した同じエージェントに利用できるメッセージの道具で渡して直させる。戻らなければ、同じ製品の実装専用エージェントに落ちるテストを添えて渡す
   - 落ちるテストが出ない周が来るか、3周したら打ち切る（理由: 周回に上限が無いと、トークンも時間も読めなくなる）。3周目で落ちたテストも直させてから打ち切り、まだ崩せそうな筋が残っていれば記録し（Issue へのコメントは承認範囲に従う）、引き渡しと PR 本文案の補足に書く
5. **記録する。** テストの区分（完了条件、断る場合、すり抜け、ランタイム）ごとの件数と、崩しにかかった周の数と各周で落ちた件数を、引き渡しと PR 本文案に残す。Claude の進行では `pr` に渡し、PR の本文の `## テストと動作確認` に書かせる（この節を省かせない）


各実装・修正の受け取り時は、(2) の最初の保存先・SHA を基準にテストと現在のテストを比較する。周回で追加したテストも、その周回の保存基準と別途比較する。コミットなら `git diff <保存したSHA> -- <対象>`、コピーなら `git diff --no-index <保存先> <現在>` を使い、削除・変更がなく追加だけであることを確かめる。後者の終了コード1は差分ありなので内容で判断する。テストが誤りと見られたら実装者が書き換えず、Issue と docs/ で判断し、決められなければ人に聞く。途中で対象と判明したら既存差分を保持し、テスト役へ実装案を渡さず役割を分け直す。
