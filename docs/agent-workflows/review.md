# 差分の点検基準

完了条件、規約、検査、動作確認、指摘の扱いの共通基準。コミットや外部操作は各製品の入口と承認範囲に従う。ここから別製品を呼ばない。

## 完了条件と突き合わせる

Issue の完了条件を 1 つずつ、差分のどこで満たされているかを確認する。
満たせていないものがあれば、実装に戻る。

続けて、差分が Issue の `やらないこと` に触れていないかを突き合わせる。`git diff <base>...HEAD --stat` の変えたパスと、入口で確認した差分の振る舞いを、`やらないこと` の行と1行ずつ見る。前の点検が足した `- 点検（` で始まる行は、突き合わせる行に数えない（理由: 完了条件を満たした実装でも、触らないと決めたものまで変えていると、人が差分を読まないかぎり誰も気づかない）。

- Issue に `やらないこと` の節が無い（節を足す前に起票した）なら、突き合わせを飛ばし、判断の差分に「節が無い」と出す。節が `（なし）` なら、判断の差分に「触れていない」と出す
- 触れていなければ、判断の差分に「触れていない」と出す
- 触れていたら、対話の実行では利用できる質問の道具で人に聞く。推す案を先頭にする（例: 戻す、触れたまま進める）。「戻す」が選ばれたら実装に戻り、直してから突き合わせ直す。答えは言い換えずに出力に残す（Issue への写しは `pr/issue-update.md` が行う。done-check は Issue を書かない）
- 人に聞けない実行（質問の道具を使えないか、答える人がいない。`claude -p` などの非対話の実行、CI の中）では、聞かずに `触れた: <パス> — <理由>` として出力に残す。PR 作成側が PR に `needs-human` を足す

あわせて、実装中に置いた判断のうち、Issue（`人が決めたこと`、`セッションが置いた前提`、やること）と `docs/` に書かれていないものを、根拠と一緒に一覧にする。PR 作成側が `セッションが置いた前提` に足せるよう、`- <日付> 実装中 <判断したスキル名>: <判断> — <根拠>` の形で書く。無ければ「無し」と出す。

## 規約を読む

CLAUDE.md と、その製品の指示、変更に関係する設定・近いコードを読む。既読で変更のない資料は読み直さない。
プロジェクトの書き方に合っているかを見る。自分の好みに寄せない。

## 機械で判定できるものを先に通す

[受け入れ条件](acceptance.md) で必要な検査を選び、[検査結果の再利用](validation.md) に従う。失敗は直し、修正の影響する検査を再実行する。

## 動かして確かめる

Issue の「確認方法」を自分で実行し、完了条件を満たすかを実際の挙動で確かめる。
確認方法が書かれていなければ、完了条件から手順を組み立てる。
ログインが要るものは、seed がローカルの D1 に入れたセッションの Cookie を使う（`docs/development.md` の「開発とテストでのログイン」）。

| 変更の及ぶ先 | 確かめ方 |
| --- | --- |
| API | `wrangler dev` を立て、Cookie を付けてリクエストを送り、レスポンスと D1 の中身を見る。組織をまたぐ操作は、別の組織の ID で呼んで 404 になることも見る |
| 画面 | 手元は利用できるブラウザで Cookie を置いて開き、操作して表示と状態を見る。ブラウザの無いクラウドのセッションは、PR の後の CI の e2e の結果で確かめる（落ちたテストの画像は成果物の `test-results/` の `test-failed-<n>.png`）。e2e はセッションが手元で走らせない（`docs/development.md` の「開発の流れ」）。変えた画面と状態を開く e2e のテストが無ければ足す。PR の本文には画像を載せない（`pr/create.md` の Step 3）。この手順では PR の本文に触らない |
| 挙動の変わらない変更（リファクタ、型、ドキュメント、設定） | 必要な機械的検査で足りる。省いた旨を出力に書く |

動かせなかった項目は、確かめられなかった項目として出力に書く（理由: 確認済みと書くと、マージの判定で人が動作確認を省く）。

## 直す

出た指摘を、直すものと直さないものに分ける。

直す指摘のうち、テストで拾えたはずのもの（振る舞いの誤り、境界の値、断るべき入力、すり抜け、前に直したものの回帰）は、直す前に、その指摘で落ちるテストを足し、落ちることを確かめてから直す（理由: 直しだけを入れると、同じ誤りがまた入っても CI が止めず、次のレビューでの見落としを待つことになる）。テストにできない指摘（読みやすさ、名前、文書、設計の好み）は、そのまま直す。

- CRITICAL と HIGH: 直す。直さないなら、その理由を出力に残す（pr が PR 本文の `## 補足` に書く）
- 直さないつもりの CRITICAL と HIGH（誤検知と見たものを含む）は、`finding-verifier` に渡して反証にかける。渡すのはレビューに渡した範囲、チェックリストのディレクトリの絶対パス、指摘の本文そのままで、自分の見立ては添えない（理由: 直さない判断を下すのは差分を書いた本人で、自分の差分を守る側に寄る）。`反証` が返れば、その根拠を直さない理由として残す。`維持` が返れば直すか、直さない理由を出力に残す
- MEDIUM と LOW: 直すか、理由を残さずに落としてよい（全件に理由を書くと PR 本文が膨らむ）

エージェントの報告の「変更外」節は、この PR では直さない（差分に無い箇所を直すと PR が膨らむ）。
CRITICAL と HIGH は、別の Issue にするかをユーザーに提案する。
