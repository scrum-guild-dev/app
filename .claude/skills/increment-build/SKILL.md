# increment-build

## 仕事

1つのタスク（または子の無いストーリー）の Issue を、実装して `done-check` に渡す。`done-check` が `pr` へ続け、PR、レビューへの対応、マージの後片付けまでを受け持つ。
終わりは「PR がマージ済み、または `needs-human` などで人に渡した状態で、`pr` が後片付けまで終えている」状態。
人が担うのは判断だけにする。判断が要る点は推す案を先頭にした `AskUserQuestion` で聞き、チャットの文章で選ばせない。

## 入力

Issue の番号。並べて進めているほかの Issue があれば、その番号と重なりうるファイル（`sprint-pick` のプロンプトが渡す）。

## 手順

### 1. 着手してよいかを確かめる

[共通の Issue 基準](../../../docs/agent-workflows/issue.md) の着手条件を読む。Issue、親、依存、既存 PR、並行作業を確認する。

### 2. 詰める

同じ文書の「詰める」に従い、信頼できる本文とコメントから目的と範囲を決める。難所だけ backlog-refine で聞く。

### 3. 記録する

同じ文書の「記録する」に従う。Issue、範囲、検証方法と、直接実装か委譲かを短く宣言する。rename-session で Issue の番号と題を付ける。

### 4. ワークツリーを切る

ブランチとワークツリーの名前 `<番号>-<短い名前>` を、ファイルを書き始める前に決める（後で名前を変えると、フックが自分の変更と数えなくなる）。

```bash
git fetch origin
git worktree add worktrees/<名前> -b <名前> origin/main
```

`post-checkout` が `status:in-progress` を付けて `status:refining` を外す。
ワークツリーで `pnpm install` を走らせる（依存はワークツリーごとに入れる。`docs/development.md` の「ワークツリーで作業する」）。
以降の git、`pnpm`、`done-check` は、ワークツリーの絶対パスの中で行う。Bash のカレントは呼び出しごとに本体へ戻るので、コマンドごとに `cd <絶対パス> ||` を付けるか `git -C <絶対パス>` で打つ。

クラウドのセッションはワークツリーを切らず、ラベルを手で付け替える（`docs/development.md` の「Issue の状態」）。
Issue に、ブランチ名とセッションの識別をコメントで残す（同じ文書の「並行して作業するときの決まり」）。

### 5. 実装する

Claude のセッション内で進め、Codex の CLI やエージェントを起動しない。
[受け入れ条件](../../../docs/agent-workflows/acceptance.md) を読み、通常は自分で実装する。分離して任せることで速くなる独立した作業だけ Claude の implementer に委譲する。小変更は引き継ぎを挟まない。
[書き手を分ける変更](../../../docs/agent-workflows/test-first.md) の対象（守る仕組み、認証・認可、Workers のランタイム）では、その手順でテスト・実装・崩す役を分ける。
委譲先はコミットせず、Edit と Write で編集する。担当範囲と受け入れ条件、検査ログ・入力状態を返させる。
実装の担い手（メインか Claude の implementer）と役割を分けた検査の結果を pr に渡す。

### 6. 受け取る

自分で書いた場合も委譲した場合も、コミット済み・未コミット・新規ファイルを確認し、範囲外や身に覚えのない差分があれば実行を止めて確かめる。
[検査結果の再利用](../../../docs/agent-workflows/validation.md) に従い、未実施・無効になった検査を行う。委譲先の成功という報告だけを結果とせず、ログと入力状態を確かめる。
テストを先に書いた場合は保存したテストとの差分も確認する。通ったらコミットし、done-check に検査記録を渡す。

### 7. 渡した後

done-check から pr へ続ける。親のある最後のタスクでは親の受け入れ条件も引き渡し、マージ後の後片付けまで進める。
原因不明の検査失敗、Issue の分割が必要、仕様から決められないテストの誤りは報告して止まる。
